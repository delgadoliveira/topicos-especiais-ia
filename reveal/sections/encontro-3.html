🧠 Parte 1: O desafio do contexto

Um LLM lê tudo a cada chamada — e paga por cada token lido.
Quando a conversa cresce, três coisas acontecem:

💸 Custo explode
🐢 Latência sobe
🧠 Qualidade cai
Vamos entender por quê — e as soluções que o mercado usa.

3.1 O problema da context window

A context window é tudo que o modelo "vê" numa única chamada: instruções + histórico + documentos + pergunta. É grande, mas finita — e cada token custa.

📏 Janelas reais (aprox., 2024-2025)
  • GPT-4o — ~128.000 tokens
  • Claude 3.5 — ~200.000 tokens
  • Gemini 1.5/2 — ~1.000.000+ tokens
1 token ≈ 4 caracteres (PT-BR). 200k tokens ≈ um livro inteiro.
💸 O custo escala rápido
custo = tokens_entrada × preço_in + tokens_saída × preço_out
Exemplo: 50k tokens/chamada × 1.000 chamadas/dia = 50M tokens/dia. Mesmo barato por chamada, em escala vira orçamento real.
⚠️ 3 problemas: (1) Limite duro — passou, a API rejeita. (2) Custo — você paga TODOS os tokens, toda chamada. (3) Lost in the middle — o modelo "esquece" o que está no meio de contextos longos (próximo slide).

Lost in the Middle — o efeito U

Pesquisadores colocaram a resposta certa em posições diferentes de um contexto longo e mediram a acurácia. O resultado tem forma de U: o modelo acerta no começo e no fim, mas "esquece" o meio.

85%Início
60%25%
45%Meio
55%75%
80%Fim
🧠 Por que acontece?
  • Atenção diluída: entre milhares de tokens, o "foco" se espalha
  • Efeitos posicionais: início e fim recebem mais peso
  • Treino: modelos viram poucos exemplos de contexto gigante
  • Ruído: a info crítica compete com muito texto irrelevante
🛠️ Como mitigar
  • Recuperar menos e melhor (RAG + reranking)
  • Ordenar o contexto por relevância
  • Instruções e evidências críticas perto da pergunta
  • Comprimir o que é longo e ruidoso
📌 Conexão com RAG: o objetivo não é "enfiar tudo no contexto" — é selecionar a evidência certa e posicioná-la bem.
📚 Liu et al. (2023) — "Lost in the Middle: How Language Models Use Long Contexts"
🧪 No caso condutor: se jogarmos todos os slides + artigos + dúvidas antigas do aluno no prompt, a evidência crítica cai justamente no "meio esquecido". Por isso selecionamos e reposicionamos.

3.2 As 4 estratégias principais

✂️ Truncamento (Sliding Window)
Mantém apenas as últimas N mensagens e descarta o resto.
  • Quando usar: chatbots simples, suporte ao cliente com conversas curtas
  • Implementação: messages = messages[-10:]
  • Risco: perde contexto antigo que pode ser crucial ("lembra que eu disse...")
📦 Usado por: ChatGPT free (antes do Memory), bots de atendimento
📝 Sumarização progressiva
Comprime mensagens antigas em um resumo gerado pelo próprio LLM.
  • Quando usar: conversas longas onde o contexto histórico importa
  • Implementação: a cada N msgs, gera resumo e substitui as antigas
  • Risco: +1 chamada LLM (custo extra), pode perder detalhes numéricos
📦 Usado por: LangChain ConversationSummaryMemory, Claude Projects
🔍 RAG (Retrieval-Augmented Generation)
Busca apenas os trechos relevantes de uma base de conhecimento externa.
  • Quando usar: base de documentos grande (manuais, código, wikis)
  • Implementação: embed query → busca vetorial → top-k docs → injeta no prompt
  • Risco: depende da qualidade do retriever e dos chunks
📦 Usado por: Perplexity, Notion AI, GitHub Copilot, Glean
🗄️ Delegação (Sub-agentes / Handoffs)
Sub-agente processa contexto pesado e devolve apenas a síntese.
  • Quando usar: tarefas que exigem contextos incompatíveis (código + docs + dados)
  • Implementação: agente A envia tarefa ao agente B, recebe resposta compacta
  • Risco: orquestração mais complexa, latência de múltiplas chamadas
📦 Usado por: Devin, OpenAI Swarm, CrewAI, AutoGen

Sumarização automática — E2E com o contexto crescendo

Rode no Colab (grátis, HF_TOKEN): a conversa cresce turno a turno; quando estoura o limite de tokens, as mensagens antigas viram um resumo e o contexto encolhe.

# 📋 Cole no Google Colab — usa Hugging Face (token gratuito HF_TOKEN)
from openai import OpenAI
from google.colab import userdata

client = OpenAI(base_url="https://router.huggingface.co/v1",
                api_key=userdata.get("HF_TOKEN"))

def count_tokens(msgs):                        # ~4 chars ≈ 1 token (PT-BR)
   return sum(len(m["content"]) // 4 for m in msgs)

def summarize(msgs):                           # chamada REAL ao Qwen (grátis)
   texto = "\n".join(f'{m["role"]}: {m["content"]}' for m in msgs)
   r = client.chat.completions.create(
       model="Qwen/Qwen2.5-7B-Instruct", max_tokens=60,
       messages=[{"role": "user", "content": f"Resuma em até 20 palavras:\n{texto}"}])
   return r.choices[0].message.content

def manage_context(msgs, limite=35):
   tok = count_tokens(msgs)
   if tok <= limite:
       print(f"   contexto: {len(msgs)} msgs / {tok} tokens  ✅ cabe")
       return msgs
   print(f"   contexto: {len(msgs)} msgs / {tok} tokens  ⚠️ estourou → sumarizando")
   resumo = summarize(msgs[:-2])              # resume tudo menos as 2 últimas
   novo = [{"role": "system", "content": f"Resumo do histórico: {resumo}"}, *msgs[-2:]]
   print(f"   → compactado para {len(novo)} msgs / {count_tokens(novo)} tokens")
   return novo

turnos = [("user", "Quero analisar as vendas do Q1"),
         ("assistant", "Claro! O Q1 fechou em R$2M."),
         ("user", "Compare com o Q2"),
         ("assistant", "Q2: R$2.8M, crescimento de 40% sobre o Q1."),
         ("user", "E a projeção do Q3?"),
         ("assistant", "Pela tendência, o Q3 deve ficar em ~R$3.2M."),
         ("user", "Resuma tudo para a diretoria")]

conversa = []
for role, content in turnos:                   # a conversa cresce a cada turno
   conversa.append({"role": role, "content": content})
   print(f"+ {role}: {content}")
   conversa = manage_context(conversa, limite=35)

A ideia central: em vez de confiar só na "memória" do modelo, busque trechos relevantes de uma base externa e injete no prompt antes de responder.

🏢 Quem usa: Perplexity (web, com citações), Notion AI / Copilot / Glean (docs internos), Cursor (codebase), Morgan Stanley (assistente p/ consultores). 📊 RAG reduz alucinação em 40-60% (Meta, 2024). 🎯 A grande sacada: RAG não deixa o modelo "mais inteligente" — dá acesso controlado a conhecimento externo e verificável.

🧮 Embeddings — texto vira coordenadas de significado

Antes de "buscar por significado", precisamos transformar texto em números. Um embedding é um vetor (centenas de números) que representa o sentido de um texto.

📍 Significado vira posição
  • "cancelar assinatura" e "encerrar plano" ficam perto
  • "receita de bolo" fica longe
  • Frases parecidas → vetores próximos, mesmo sem palavras iguais
Na prática são 384–1536 dimensões: imagine um mapa, mas com centenas de eixos.
🔎 Como a busca funciona
  • Similaridade = medir o ângulo/distância entre vetores (cosseno)
  • Vector DB = índice que acha rapidamente os vetores mais próximos
  • Top-k = os k pedaços mais parecidos com a pergunta
"Como cancelo?"
→
[0.12, -0.4, 0.9, …]
→
vizinhos próximos
→
chunks relevantes
💡 É isso que diferencia RAG de um Ctrl+F: busca por significado, não por palavra exata. "Carro" encontra "automóvel".

🧭 Busca semântica na prática — experimente

Um Vector DB guarda cada texto como um vetor e acha os vizinhos mais próximos. Aqui os embeddings são de verdade (modelo multilíngue rodando no seu navegador). Digite duas palavras e veja a distância semântica.

Projeção 2D aproximada (eixos didáticos: animal↔objeto, pequeno↔grande). Palavras próximas ≈ significados próximos.
Clique em comparar para carregar o modelo multilíngue (~120MB na 1ª vez, depois fica em cache) e calcular.
💡 Cosseno ≈ 1 → muito parecido; ≈ 0 → sem relação. É exatamente essa conta que o Vector DB faz para achar os top-k chunks de um RAG. Palavras ambíguas ("banco", "manga") dependem de contexto.

Da pergunta à resposta — busca, ranking e síntese

A pergunta vira vetor, medimos a similaridade contra cada chunk, ordenamos, pegamos o top-k como ground data e o modelo sintetiza a resposta a partir DELE.

🔎 "Como cancelo minha assinatura?" → [0.12, -0.4, 0.9, …]
Ranking por similaridade de cosseno (−1 a 1):
0.83"Para cancelar o Plano Premium: Config → Assinatura → Cancelar." ✅
0.71"O cancelamento vale até o fim do ciclo de cobrança." ✅
0.34"Para trocar a forma de pagamento: Config → Pagamento."

🎯 O modelo não inventou: cada afirmação veio de um chunk recuperado. Trocar o ranking (melhor embedding, reranker) muda o que entra no ground data — e portanto a resposta.

RAG do zero — ranking + síntese (E2E no Colab)

Sem framework: sentence-transformers gera os vetores, numpy rankeia por cosseno e o Qwen (grátis) sintetiza. Os logs mostram embedding, ranking e ground data.

# 📋 Colab:  !pip install -q sentence-transformers numpy openai
from sentence_transformers import SentenceTransformer
import numpy as np
from openai import OpenAI
from google.colab import userdata

# 1. Base de conhecimento (em produção: seus documentos fatiados em chunks)
chunks = [
   "Para cancelar o Plano Premium: Config → Assinatura → Cancelar (vale no fim do ciclo).",
   "Reembolsos são processados em até 5 dias úteis após a solicitação.",
   "O Plano Premium inclui suporte prioritário e relatórios avançados.",
   "A central de ajuda atende de segunda a sexta, das 9h às 18h.",
   "Para trocar a forma de pagamento: Config → Pagamento.",
]

# 2. Cada frase vira um vetor de 384 números (embedding local, grátis)
embedder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
base = embedder.encode(chunks, normalize_embeddings=True)

# 3. A pergunta também vira vetor → rankeia por similaridade de cosseno
pergunta = "Como cancelo minha assinatura?"
q = embedder.encode([pergunta], normalize_embeddings=True)[0]
scores = base @ q                               # 1 número por chunk (−1 a 1)
ranking = np.argsort(scores)[::-1]

print(f"Pergunta → embedding: {q[:3].round(2)}...  (384 dims)\n")
print("Ranking (vizinhos mais próximos):")
for i in ranking:
   print(f"  {scores[i]:.2f}  {chunks[i]}")

# 4. Top-2 = ground data injetado no prompt; o modelo sintetiza SÓ com ele
contexto = [chunks[i] for i in ranking[:2]]
print("\n📚 Ground data:", *contexto, sep="\n  • ")
client = OpenAI(base_url="https://router.huggingface.co/v1", api_key=userdata.get("HF_TOKEN"))
resp = client.chat.completions.create(
   model="Qwen/Qwen2.5-7B-Instruct", max_tokens=120,
   messages=[{"role": "user", "content":
       "Responda usando APENAS o contexto:\n- " + "\n- ".join(contexto) + f"\n\nPergunta: {pergunta}"}])
print("\n🤖 Resposta sintetizada:\n", resp.choices[0].message.content)

1️⃣ Loaders
Lêem o conteúdo bruto: PDF (PyPDF), HTML (BeautifulSoup), Markdown, Word, planilhas (Unstructured).
2️⃣ Splitters (chunking)
Quebram o texto em pedaços indexáveis: RecursiveCharacterTextSplitter, SemanticChunker, ou por cabeçalho (Markdown).
3️⃣ Embeddings
Transformam cada chunk em vetor. HF sentence-transformers (grátis, local), BGE, Cohere. Dimensão típica: 384–1024.
🔪 O dilema do chunking — tamanho × contexto
📏 Pequeno (~200 tok): busca precisa, mas perde o contexto ao redor
📐 Grande (~1000 tok): preserva contexto, mas traz ruído e dilui o match
🔗 Overlap (~50 tok): evita cortar uma ideia no meio entre dois chunks
📌 Exemplo: num regulamento acadêmico, se você separar "prazo de matrícula" do parágrafo que explica as exceções, o RAG responde errado. Chunk por seção/parágrafo > cortar texto cegamente.

Hands-on: RAG completo com Chroma — E2E

100% grátis no Colab: embeddings locais (sentence-transformers) + vector DB Chroma + síntese com Qwen 2.5 via HF router. retrieve → inject → generate.

# 📋 Colab: !pip install -q langchain-chroma langchain-huggingface sentence-transformers chromadb openai
from langchain_core.documents import Document
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_chroma import Chroma
from openai import OpenAI
from google.colab import userdata

# 1. Documentos (em produção: carregados de PDF/txt e fatiados em chunks)
docs = [Document(page_content=t) for t in [
   "Para cancelar o Plano Premium: Config → Assinatura → Cancelar (vale no fim do ciclo).",
   "Reembolsos são processados em até 5 dias úteis após a solicitação.",
   "O Plano Premium inclui suporte prioritário e relatórios avançados.",
   "Para trocar a forma de pagamento: Config → Pagamento.",
]]

# 2. Embeddings locais (grátis) + índice vetorial Chroma
embeddings = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
vstore = Chroma.from_documents(docs, embeddings)
retriever = vstore.as_retriever(search_kwargs={"k": 2})

# 3. Busca semântica: recupera os 2 chunks mais próximos ("ground data")
pergunta = "Como cancelo minha assinatura?"
encontrados = retriever.invoke(pergunta)
print("📚 Chunks recuperados:")
for d in encontrados:
   print("  •", d.page_content)

# 4. Injeta o contexto no prompt e sintetiza (Qwen grátis via HF router)
contexto = "\n".join(d.page_content for d in encontrados)
client = OpenAI(base_url="https://router.huggingface.co/v1", api_key=userdata.get("HF_TOKEN"))
resp = client.chat.completions.create(
   model="Qwen/Qwen2.5-7B-Instruct", max_tokens=120,
   messages=[{"role": "user",
       "content": f"Responda usando SÓ o contexto:\n{contexto}\n\nPergunta: {pergunta}"}])
print("\n🤖 Resposta:", resp.choices[0].message.content)
⚠️ O antigo langchain.chains / create_retrieval_chain saiu do LangChain 1.x. O padrão atual: retriever.invoke() + montar o prompt na mão. Rate limit do modelo grátis: ~5 req/min.

Advanced RAG — quando o básico não basta

🚨 Caso real: Uma fintech implementou RAG básico para FAQ. Resultado: 45% das respostas erradas — (1) pergunta ambígua, (2) o chunk certo ficava abaixo do top-5, (3) info contraditória de versões antigas.

RAG ingênuo (embeddings + top-K) falha em 4 lugares. Advanced RAG não é uma esteira fixa — é uma caixa de ferramentas: para cada falha, uma técnica.

🔪 Chunking — o que é um chunk e por que importa

O que é um chunk? É um pedaço de texto em que quebramos cada documento antes de gerar embeddings. O RAG nunca busca "o documento inteiro" — ele indexa, recupera e cita chunks. Cada chunk vira um vetor no Vector DB e é a menor unidade que pode ser recuperada.
📄 Exemplo — o manual do Plano Premium quebrado em chunks
chunk_1 · "Para cancelar o Plano Premium: Config → Assinatura → Cancelar."
chunk_2 · "O cancelamento vale até o fim do ciclo de cobrança."
chunk_3 · "Reembolsos são processados em até 5 dias úteis."
A pergunta "Como cancelo?" vira vetor e bate forte em chunk_1 e chunk_2 — só esses dois entram no contexto do LLM. Se o corte tivesse grudado o passo de cancelar com o horário da central, o match ficaria diluído.

O tamanho e onde cortar mudam tudo. Quatro estratégias:

Chunk fixo
corta a cada N tokens: barato, mas separa ideias no meio
Semantic chunking
corta nas junções de tópico: cada chunk = uma ideia coesa
Proposition chunking
uma afirmação por unidade ("o prazo é 30 dias")
Parent-child
busca pelo pedaço pequeno, devolve o bloco grande (adiante)
🎨 Analogia: um PDF é uma régua. Fixo corta em blocos iguais (rápido, mas parte frases). Semantic corta nas junções de assunto. Parent-child mantém uma "moldura" maior ao redor do trecho encontrado — o LLM recebe o contexto vizinho e não responde fora de contexto.

🏗️ Arquiteturas avançadas de RAG

Quando o RAG simples (chunk → embed → top-k → gerar) falha, estas arquiteturas atacam falhas específicas: relações entre entidades, visão global de muitos docs, memória entre sessões e auto-crítica da recuperação.

🕸️ GraphRAG
Transforma documentos em um grafo de entidades e relações. Resolve: perguntas multi-hop ("quem influencia quem?", "que cláusulas dependem da 14.3?") que o top-k plano não conecta, porque a resposta está espalhada em vários docs.
🌳 RAPTOR
Constrói uma árvore de resumos (folhas = chunks; nós = resumos de resumos). A busca sobe/desce níveis. Resolve: perguntas que exigem visão global ("resuma o contrato inteiro") sem estourar o context window.
🧠 MemoRAG
Mantém uma memória de interações e documentos passados e a usa como pista para recuperar. Resolve: continuidade entre sessões ("como no caso que discutimos semana passada").
🩺 Self-RAG / CRAG
O sistema critica a própria recuperação: "preciso buscar?", "o que veio é suficiente?", "devo corrigir/rebuscar?". Resolve: chunks irrelevantes e alucinação por contexto ruim — descarta ou refaz a busca antes de responder.
⚠️ Arquitetura avançada não é prêmio por sofisticação. Cada uma custa ingestão/latência. Use quando o diagnóstico mostrar que o RAG simples não resolve aquela falha específica.

Padrão 2 · Multi-Query & HyDE

🔁 Multi-Query
Gere N reformulações da pergunta e busque com todas para aumentar recall.
# 📋 Colab: !pip install -q openai  (reusa o client do slide anterior)
def multi_query(pergunta, n=4):
    r = client.chat.completions.create(model="Qwen/Qwen2.5-7B-Instruct", max_tokens=120,
        messages=[{"role": "user", "content":
            f"Gere {n} reformulações da pergunta, uma por linha, sem numerar:\n{pergunta}"}])
    return [q.strip("-• ") for q in r.choices[0].message.content.split("\n") if q.strip()]

queries = multi_query("Como cancelo o Plano Premium?")
docs = []
for q in queries:
    docs += vectordb.search(q, k=5)   # busca com TODAS → mais recall
docs = list({d.id: d for d in docs}.values())   # dedupe por id
print(queries)
📈 Na prática, costuma melhorar o recall em 20–40%.

Padrão 2 · Multi-Query & HyDE — continuação

🎭 HyDE (Hypothetical Document Embeddings) cria uma resposta hipotética e usa o embedding dela para buscar.
# 📋 reusa o client. HyDE: gera resposta hipotética e busca com o embedding DELA
def hyde(pergunta):
    r = client.chat.completions.create(model="Qwen/Qwen2.5-7B-Instruct", max_tokens=80,
        messages=[{"role": "user", "content":
            f"Escreva um parágrafo curto que RESPONDERIA a pergunta:\n{pergunta}"}])
    return r.choices[0].message.content.strip()

hipo = hyde("Como cancelo o Plano Premium?")
docs = vectordb.search(hipo, k=5)   # embedding da resposta hipotética → busca
print(hipo)
💡 Funciona porque “resposta → resposta” costuma ficar mais perto no espaço vetorial que “pergunta → resposta”.

Padrão 3 · Parent-Child Chunks & Agentic RAG

👨‍👦 Parent-Child Chunks
Indexe pedaços pequenos (child) para busca precisa, mas devolva ao LLM o pedaço grande (parent) para manter contexto rico.
❓ O que é o "parent"? É o bloco original grande de onde o child foi recortado — por exemplo a seção inteira do manual. O child ("Para cancelar: Config → Assinatura") é ótimo para casar com a pergunta, mas curto demais para responder. Guardamos o vínculo child.parent_id → parent e, ao achar o child, entregamos o parent inteiro ao LLM.
# parent = seção grande;  children = frases pequenas indexadas
parent = {"id": "sec_cancelamento", "text": "CANCELAMENTO. Para cancelar acesse "
          "Config → Assinatura → Cancelar. Vale até o fim do ciclo. Reembolso em 5 dias."}
children = [{"text": t, "parent_id": parent["id"]} for t in
            ["Para cancelar: Config → Assinatura → Cancelar.",
             "O cancelamento vale até o fim do ciclo de cobrança."]]
# busca casa no CHILD (preciso) → devolve o PARENT (contexto) ao LLM
achou = children[0]                       # match do retriever
contexto = parent["text"] if achou["parent_id"] == parent["id"] else achou["text"]
print(contexto)   # LLM recebe a seção inteira, não só a frase curta

Depois de recuperar — Reranking & Compression

Recuperar é só metade. Os dois passos finais decidem o que e quanto chega ao LLM.

🎯 Reranking — uma segunda leitura
O retriever rápido traz ~20 candidatos. O reranker (cross-encoder) lê a pergunta + cada trecho com atenção e reordena os 3-5 melhores.
  • Busca vetorial pergunta: "esses textos são parecidos?"
  • Reranker pergunta: "este trecho responde esta pergunta?"
📦 Cohere Rerank, BGE-reranker, cross-encoder (sentence-transformers)
🗜️ Context Compression — cortar o ruído
Antes de enviar ao LLM, remove sentenças irrelevantes dos chunks recuperados, mantendo só o que responde à pergunta.
  • Menos tokens → mais barato e rápido
  • Menos ruído → combate o "lost in the middle"

Search híbrido — porque puro vetor não basta

Busca semântica entende significado, mas tropeça em termos exatos: IDs, datas, códigos, siglas. A solução: combinar semântico (vetor) + lexical (BM25).

🧪 Onde o vetor sozinho falha: a pergunta "status do chamado 504-A?". O embedding aproxima "chamado" de "ticket/atendimento", mas não sabe que "504-A" é um código literal — pode devolver o chamado 502 ou 540. O BM25 casa exatamente o token "504-A" e traz o documento certo.

🧠 Semântico (vetor)
Compara o significado via cosseno entre embeddings. Acerta sinônimos e paráfrases ("cancelar" ≈ "encerrar plano"). Falha em números, códigos e nomes próprios raros, que viram vetores parecidos.
🔤 Lexical / BM25
É um Ctrl+F turbinado: pontua o doc pela presença dos termos exatos da pergunta, dando mais peso a palavras raras (um "504-A" vale mais que um "o"). Acerta "CPF 123", "SKU-9", "erro 504". Falha em paráfrases: "carro" não encontra "automóvel".
🔀 Merge + rerank: unimos as duas listas (ex.: Reciprocal Rank Fusion) e um reranker cross-encoder (Cohere Rerank, BGE-reranker) relê a pergunta + cada trecho e reordena os top-20 pela relevância real. Cada estágio soma +5-15% em benchmarks (BEIR, MS MARCO). Use só os que sua falha pedir.

🔧 Como se faz fine-tuning de LLM hoje

Ninguém retreina os bilhões de pesos do zero. O padrão moderno é PEFT (Parameter-Efficient Fine-Tuning): congela o modelo base e treina só um adaptador minúsculo por cima.

1️⃣ Monte um dataset de exemplos
Pares {entrada → saída ideal}. Ex.: 500 e-mails já rotulados, ou 300 pares pergunta→resposta no seu tom. Qualidade > quantidade (algumas centenas de bons exemplos já mudam muito).
2️⃣ SFT com LoRA / QLoRA
SFT (Supervised Fine-Tuning): o modelo vê a entrada, compara sua saída com a ideal e ajusta. LoRA treina matrizes pequenas "coladas" nas camadas (0,1–2% dos pesos). QLoRA = LoRA + base em 4-bit → cabe numa GPU grátis do Colab.
3️⃣ (Opcional) Alinhamento por preferência
DPO / RLHF: em vez de "a resposta certa", você dá pares "esta é melhor que aquela" e o modelo aprende a preferir o estilo/decisão desejado.
4️⃣ Sirva o adaptador
O adaptador LoRA tem poucos MB. Você carrega o modelo base + adaptador. Ferramentas: HF peft / trl, Axolotl, Unsloth; ou APIs gerenciadas (OpenAI, Together).
💡 Ordem na prática: comece com prompt engineering. Só parta para fine-tuning quando (a) o comportamento precisa ser consistente em escala, (b) você tem exemplos rotulados e (c) o prompt já não dá conta. Para conhecimento factual que muda, use RAG — fine-tuning não "decora fatos" de forma confiável.

Caso concreto · resposta bonita, evidência fraca

❓ Pergunta do usuário: "Qual é o prazo de aviso prévio para cancelar o contrato com um fornecedor?"
📚 Contexto recuperado (3 chunks, 3 fontes diferentes)
[doc_1] Contrato v2 (2022): "aviso prévio de 30 dias." ← versão antiga, substituída

[doc_2] Contrato v3 (2024, vigente): "aviso prévio de 60 dias para fornecedores críticos." ← vigente, mas com escopo restrito

[doc_3] E-mail informal: "podemos tentar 45 dias." ← negociação, não é contrato
🤖 Resposta ruim (o que o modelo gerou)
"O contrato exige aviso prévio de 45 dias."

Por que é ruim:
• pegou o número do e-mail, que não é fonte oficial;
• misturou as versões v2 e v3;
• ignorou o escopo "fornecedores críticos";
• não citou cláusula → não é auditável.
✅ Síntese correta e auditável
"Para fornecedores críticos, o contrato vigente (v3) exige 60 dias de aviso prévio [contrato_v3, cláusula 14.3]. Para os demais fornecedores, o contexto recuperado não traz regra — é preciso confirmar antes de afirmar."
🎯 Pergunta que o aluno deve fazer
"Eu consigo clicar na evidência e verificar a frase?" Se não, ainda não há grounding suficiente. Boa síntese escolhe a fonte certa (vigente e oficial), respeita o escopo e admite o que não sabe.

Grounding, attribution e citation — não são a mesma coisa

🎯 Grounding
A resposta usa apenas evidências disponíveis no contexto recuperado.
🧾 Attribution
Cada afirmação importante é ligada a uma evidência específica.
🔖 Citation
A evidência aparece para o usuário como fonte, link, trecho, página ou chunk.
Uma resposta pode ter citação falsa, pode citar um documento real mas não suportar a frase, ou pode estar fiel ao documento errado. Por isso precisamos medir, não só “pedir para citar”.

Por que grounding falha mesmo com RAG?

1. Fonte recuperada errada
Retriever achou versão antiga, e-mail tangencial ou chunk com termo parecido.
2. Fonte certa, leitura errada
LLM ignora qualificadores como “apenas”, “exceto”, “fornecedores críticos”.
3. Citação decorativa
O modelo coloca [doc_2] no fim da frase, mas doc_2 não sustenta aquela afirmação.
4. Síntese mistura fontes
Combina número de uma fonte, escopo de outra e conclusão inventada.
⚖️ Caso real — Mata v. Avianca (2023): advogados usaram o ChatGPT para escrever uma petição e ele inventou 6 precedentes (ex.: "Varghese v. China Southern Airlines") que não existem. Quando o juiz pediu as íntegras, o modelo fabricou as decisões, e os advogados as entregaram. O juiz P. Kevin Castel os multou em US$ 5.000 (S.D.N.Y., 22/06/2023, caso 1:22-cv-01461). Citação plausível ≠ citação verdadeira — por isso grounding mede, não confia. ↗ fonte

Técnicas de grounding — quatro camadas

1. IDs estruturados
Cada chunk entra no prompt com doc_id, página, seção, data e versão.
2. Citação inline
Peça fonte após cada afirmação verificável, não apenas uma lista no final.
3. Recusa explícita
Se o contexto não suporta a resposta, o agente deve dizer “não encontrei nos documentos”.
4. Verificador externo
Segundo passo classifica claims como suportadas, parciais ou não suportadas.

O problema da Synthesis

Recuperei 20 chunks de 5 fontes. E agora?

📄 Doc A diz: "X é 30%"
📄 Doc B diz: "X é 40%"
📄 Doc C diz: "X cresceu em 2024"
📄 Doc D contradiz Doc A
📄 Doc E é tangencial
🧬 Synthesizer → resposta única, coerente, citando conflitos
Synthesis ≠ Retrieval. É um passo de raciocínio que requer: dedup, resolução de conflito, hierarquização, citação atribuída.

Padrão 1 · Map-Reduce sobre documentos

Para muitos docs ou docs grandes — não cabem todos no contexto.

Doc 1
Doc 2
Doc N
↓
Map: extrai info relevante
→
Reduce: combina, resolve conflitos, responde
Map: rodar em paralelo, barato (modelo menor). Reduce: modelo maior, com instruções de citação.
Variante: Refine — atualiza resposta incrementalmente conforme lê cada doc.

Padrão 2 · Resolução de conflitos (E2E)

Quando fontes discordam, o agente não pode simplesmente escolher uma nem tirar média.

Padrão 2 · Resolução de conflitos — o resultado

🤖 Saída esperada (o Qwen sintetiza sem escolher lado nem tirar média):

✅ O que ele fez certo

⚠️ Anti-padrão clássico
"Média de alucinações": pegar 30% e 40% e responder "35%". Pior que escolher um: inventa um dado que nenhuma fonte afirma e parece confiante.

Padrão 3 · Hierarchical Summarization

Quando o corpus é grande demais para caber no context window (um livro, um repositório inteiro, milhares de tickets), não dá para "jogar tudo no prompt". A ideia é resumir em níveis: comprimir muitos chunks em poucos sumários, e esses em um sumário ainda menor, até caber.

Chunks
milhares
→
Sumário lvl 1
1 por seção
→
Sumário lvl 2
1 por documento
→
Resposta final
citando origens
🧱 Exemplo concreto (repositório)
lvl 0: cada arquivo vira chunks. lvl 1: "este arquivo faz autenticação JWT". lvl 2: "este módulo cuida de login e sessão". A pergunta "onde valido o token?" desce do lvl 2 → lvl 1 → chunk exato.
🔗 Ponteiros preservam a origem
Cada sumário guarda o id do nível anterior que o gerou. Assim a resposta final não cita "o resumo", e sim o chunk original (arquivo, linha, cláusula) — mantendo grounding auditável mesmo após 2 níveis de compressão.
🏭 Usado em produção: Claude Projects e NotebookLM (resumo de dezenas de docs), Cursor codebase indexing (mapa hierárquico do repo). 🎯 Escolha o nível pela pergunta: visão global → lvl 2; detalhe pontual → desça até o chunk.

from openai import OpenAI
from google.colab import userdata
client = OpenAI(base_url="https://router.huggingface.co/v1", api_key=userdata.get("HF_TOKEN"))
def llm(msg, mx=180):
   return client.chat.completions.create(model="Qwen/Qwen2.5-7B-Instruct",
       max_tokens=mx, messages=[{"role": "user", "content": msg}]).choices[0].message.content.strip()

docs = [
   "Rel. 2023: rotatividade de fornecedores foi de 30%.",
   "Rel. 2024: rotatividade subiu para 40%.",
   "Nota interna: parte do aumento veio de fornecedores sazonais.",
]
# MAP: extrai o essencial de cada doc (barato, paralelizável)
mapa = []
for i, d in enumerate(docs, 1):
   frase = llm(f"Extraia em 1 frase o dado central:\n{d}", 50)
   mapa.append(frase)
   print(f"[MAP doc_{i}] {frase}")                      # 👀 log por documento

# REDUCE: junta os sumários e sintetiza citando [doc_x]
ctx = "\n".join(f"[doc_{i}] {m}" for i, m in enumerate(mapa, 1))
print(f"\n[CONTEXTO montado — {len(ctx)} chars]\n{ctx}")   # 👀 log do contexto crescendo
final = llm("Sintetize citando [doc_x]. Se houver conflito, mostre as duas "
            f"visões e a causa provável.\n{ctx}\n\nPergunta: Como evoluiu a rotatividade?")
print(f"\n[REDUCE — resposta final]\n{final}")           # 👀 log da síntese

🔎 Onde o prompt de síntese roda dentro do agente

A síntese não é uma etapa à parte: é a última chamada do agente de RAG. Retrieve e augment só preparam o prompt; a síntese é o GENERATE destacado abaixo.

# 📋 Colab: !pip install -q sentence-transformers numpy openai
from sentence_transformers import SentenceTransformer
import numpy as np
from openai import OpenAI
from google.colab import userdata

embedder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
client = OpenAI(base_url="https://router.huggingface.co/v1", api_key=userdata.get("HF_TOKEN"))
BASE = ["Para cancelar: Config → Assinatura → Cancelar.",
        "O cancelamento vale até o fim do ciclo de cobrança.",
        "Reembolsos são processados em até 5 dias úteis."]
VEC = embedder.encode(BASE, normalize_embeddings=True)

def agente_rag(pergunta):
    q = embedder.encode([pergunta], normalize_embeddings=True)[0]
    top = np.argsort(VEC @ q)[::-1][:2]                 # 1) RETRIEVE (vizinhos próximos)
    contexto = "\n".join(BASE[i] for i in top)           # 2) AUGMENT (monta o contexto)
    prompt = f"Responda usando SÓ o contexto:\n{contexto}\n\nPergunta: {pergunta}"
    resp = client.chat.completions.create(               # 3) GENERATE ← aqui roda a SÍNTESE
        model="Qwen/Qwen2.5-7B-Instruct", max_tokens=120,
        messages=[{"role": "user", "content": prompt}])
    return resp.choices[0].message.content

print(agente_rag("Como cancelo minha assinatura?"))
🎯 A síntese é a etapa GENERATE: montamos o prompt (contexto + pergunta + regras de citação) e chamamos o LLM. Reranking, grounding e resolução de conflito são variações desse prompt ou passos antes desta chamada.

RAG responde “o que sei nos documentos?”
Memória responde “o que este agente precisa carregar ao longo do tempo?”
Chatbots pessoais

📌 Por que virou diferencial de produto: memória reduz repetição, personaliza respostas e dá continuidade entre sessões — o usuário sente que o agente "lembra" dele.
🧪 No caso condutor: é a memória que faz o assistente lembrar as "dúvidas anteriores" e as preferências do aluno entre uma aula e outra — sem ele repetir tudo.

Context Engineering — o novo nome do jogo

Não é “escrever prompt melhor”. É projetar o fluxo de contexto.
1. Selecionar
Quais docs, memórias, tool results e exemplos entram agora?
2. Filtrar
O que fica fora para evitar ruído, custo e “lost in the middle”?
3. Ordenar
System, instruções, memória, evidências e pergunta competem por atenção.
4. Atualizar
Depois da resposta: guardar fato novo, resumir episódio ou esquecer?

Memória em camadas: mesa, armário e biblioteca

Um agente não tem "uma memória só". Ele tem camadas com custos e durações diferentes — como um trabalhador que tem a mesa à frente, um armário ao lado e uma biblioteca no prédio.

🪑 Mesa = Working memory
O context window: o que está ativo agora. Rápido de usar, mas caro e limitado (poucos milhares de tokens) e some ao fim da sessão. Só cabe o essencial do momento.
🗄️ Armário = Long-term memory
Memória persistente do agente sobre este usuário/projeto: fica salva entre sessões e é recuperada quando relevante. É o que faz o agente "lembrar de você" amanhã.
📚 Biblioteca = RAG
Conhecimento externo (documentos da empresa, manuais) que não é "sobre você", mas é buscado sob demanda com evidências/citação. Grande, compartilhado, versionado.
🔄 As políticas decidem o fluxo entre camadas: o que promover da mesa para o armário (salvar), o que trazer do armário/biblioteca para a mesa (recuperar) e o que esquecer. Sem política, a mesa entope ou o agente esquece o que importa.

Camadas × tipos: onde mora ≠ o que é

Duas classificações diferentes que confundem porque falam de coisas distintas:

🏠 Camadas (mesa/armário/biblioteca)
Respondem ONDE a informação vive e por quanto tempo/custo: working memory, long-term, RAG externo. É uma dimensão de infraestrutura.
🏷️ Tipos (episódica/semântica/procedural)
Respondem QUE tipo de conteúdo é guardado: um evento, um fato estável, um procedimento. É uma dimensão de conteúdo.
🔗 A relação: qualquer tipo pode ser guardado no armário (long-term) e trazido para a mesa quando útil. Exemplos concretos:

3.6 Skills — capacidades reutilizáveis

📅 Lançado pela Anthropic em outubro/2025.

Conceito: uma "skill" é uma pasta com:

  • Um SKILL.md descrevendo o que faz e quando usar
  • Scripts auxiliares (Python, bash)
  • Templates, dados, recursos

O agente descobre skills disponíveis e carrega só o necessário quando relevante.

~/.claude/skills/
├── pdf-extractor/
│   ├── SKILL.md          ← "use isto para extrair texto de PDFs"
│   └── extract.py
├── jira-integration/
│   ├── SKILL.md
│   └── jira_client.py
└── excel-formatter/
    ├── SKILL.md
    └── format.py
🧠 Por que importa: sem skills, você teria que incluir TODA a documentação de TODAS as ferramentas no system prompt — estourando a janela de contexto e o orçamento. Skills resolvem isso com carregamento preguiçoso.

Skills vs Tools — qual a diferença?

Ambas dão capacidades ao agente, mas operam em níveis diferentes: a tool é uma função pontual; a skill é uma competência completa carregada sob demanda.

🛠️ Tool
  • Sempre disponível — declarada no início da sessão
  • Schema JSON fixo (nome, args, descrição)
  • 1 função = 1 tool (granularidade baixa)
  • ⚠️ Ocupa contexto mesmo parada: 50 tools = 50 schemas no prompt
🎓 Skill
  • Carrega sob demanda — só quando o agente decide usar
  • Pode trazer docs, scripts e templates juntos
  • 1 skill = competência inteira ("fazer um relatório financeiro")
  • ✅ Quase zero overhead até ser ativada
📌 Use tools para ações atômicas (buscar, calcular, enviar). Use skills para empacotar um fluxo inteiro com seu conhecimento — evitando lotar o contexto com tudo o tempo todo.
💡 Analogia: tool é função da biblioteca padrão; skill é um pacote especializado que você só carrega quando precisa.
🎯 Impacto prático: com 5 tools registradas, ~500 tokens de overhead. Com 50 skills possíveis mas só 3 carregadas, ~300 tokens. Skills escalam melhor para agentes com muitas capacidades.

MCP em ação — servidor mínimo (Python)

Um servidor MCP é só um arquivo Python que declara tools com @mcp.tool(). O decorator transforma a função (nome + tipos + docstring) no schema que o cliente descobre.

# pip install "mcp[cli]"
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("minha-calculadora")

@mcp.tool()
def somar(a: int, b: int) -> int:
    """Soma dois números inteiros."""
    return a + b

@mcp.tool()
def multiplicar(a: int, b: int) -> int:
    """Multiplica dois números inteiros."""
    return a * b

if __name__ == "__main__":
    mcp.run()   # roda via stdio (JSON-RPC)
💡 A docstring vira a descrição que o LLM lê para decidir quando chamar a tool — escreva-a com cuidado.

MCP em ação — como conectar o servidor

3.8 Padrões multi-agente

🚨 Quando um agente não basta: Cursor tentou um único agente para "review + edit + test + deploy". Resultado: contexto estourava, qualidade caía após 10 passos. Solução: supervisor + workers especializados. Cada worker foca em 1 skill com contexto limpo.
🧪 No caso condutor: "explique RAG + cite fontes + sugira exercícios" são três skills distintas — um supervisor delega cada uma a um worker com contexto limpo, em vez de um agente sobrecarregado.
1. Supervisor / Orchestrator
Supervisor
→
A / B / C
Um agente central decide qual especialista chamar e agrega os resultados. Os workers não se falam diretamente.
🎯 Quando: tarefas com sub-domínios claros
📦 Ex: customer support (router → billing/tech/sales)
2. Handoff / Swarm

Agente 2
→

Cada agente passa o bastão ao próximo quando termina sua parte. Fluxo sequencial, como uma linha de produção.
🎯 Quando: pipeline com etapas ordenadas
📦 Ex: pesquisar → escrever → revisar (OpenAI Swarm)

Múltiplos níveis: um agente coordena gerentes, que coordenam workers. Escala para tarefas grandes e complexas.
🎯 Quando: projetos grandes, muitos sub-objetivos
📦 Ex: "empresa de agentes" gerando um relatório completo
🔑 Todos compartilham a mesma ideia: dividir para conquistar — cada agente tem contexto e ferramentas próprios, evitando o "agente faz-tudo" que satura.

Quando usar multi-agente?

Multi-agente adiciona complexidade (mais chamadas, mais custo, mais latência, mais pontos de falha). Só compensa quando a tarefa realmente pede divisão.

✅ Use quando
  • Fases bem diferentes (pesquisar → escrever → revisar)
  • Cada etapa precisa de prompt/contexto distinto
  • Especialistas com ferramentas próprias (um busca, outro calcula)
  • Paralelismo gera ganho real de tempo
❌ Evite quando
  • Um único agente já resolve com bom contexto
  • Latência é crítica (cada agente = +1 round-trip)
  • O custo precisa ser previsível e baixo
  • Você ainda não mediu o benefício real
🎯 Regra prática: single-agent com bom contexto costuma vencer; só vá de multi-agent quando a tarefa pedir especialização ou paralelismo — e meça antes de adotar.
🏢 Realidade do mercado (2025): segundo a Anthropic, ~90% dos agentes em produção são single-agent. Multi-agent brilha em: coding assistants (planner + coder + reviewer), research (pesquisador + escritor), e customer support (router + especialistas).

Frameworks multi-agente

Cada framework implementa os padrões anteriores com filosofias diferentes:

👥 CrewAI
"Crew" de agentes com roles (researcher, writer, reviewer). Sintaxe declarativa.
  • Filosofia: modela uma equipe humana — cada agente tem cargo, objetivo e backstory
  • Padrão típico: sequencial (handoff) ou hierárquico
  • Ideal para: protótipos rápidos, fluxos role-based intuitivos
💬 AutoGen (Microsoft)
Agentes conversam entre si em loop até resolver. Forte em código colaborativo.
  • Filosofia: diálogo entre agentes (ex: coder ↔ executor de testes)
  • Padrão típico: conversação em grupo (group chat)
  • Ideal para: geração de código, debate/refinamento iterativo
🔄 LangGraph (multi-agent)
Cada nó do grafo = 1 agente. Controle total sobre o fluxo. Padrão moderno.
  • Filosofia: grafo explícito de estados e transições — você desenha o fluxo
  • Padrão típico: qualquer um (supervisor, handoff, hierárquico)
  • Ideal para: produção, fluxos complexos com loops e condicionais
⚡ OpenAI Agents SDK (ex-Swarm)
Handoffs leves entre agentes. Minimalista, baixo overhead.
  • Filosofia: simplicidade — agentes "transferem" a conversa via function calls
  • Padrão típico: handoff/swarm sequencial
  • Ideal para: roteamento simples, quando você quer pouco "framework"
📌 Como escolher? Protótipo role-based → CrewAI · Código colaborativo → AutoGen · Produção/controle total → LangGraph · Roteamento mínimo → OpenAI Agents SDK

Exemplo: Crew com CrewAI

📖 Em palavras: imagine uma equipe de funcionários. Cada Agent tem um cargo (role), um objetivo e um "currículo" (backstory) — isso vira parte do prompt dele. Cada Task é uma entrega esperada, atribuída a um agente. O Crew orquestra: o pesquisador entrega, o escritor pega o resultado dele como contexto e produz o artigo. Divisão de trabalho automatizada.

)
escritor = Agent(
    role="Escritor técnico",
    goal="Transformar pesquisa em artigo claro",
    backstory="Você escreve para devs juniores.",
)

3.9 Hands-on integrado — agente com RAG + memória

📋 Colab-ready — usa HuggingFace InferenceClient (token gratuito)
# 📋 Execute no Google Colab — requer client do setup
from typing import TypedDict

# --- Base de conhecimento local (simula vector store) ---
KNOWLEDGE_BASE = [
    "RAG combina retrieval com geração para reduzir alucinações.",
    "Memória persistente permite continuidade entre sessões.",
    "Vector stores indexam documentos por similaridade semântica.",
    "ChromaDB é um vector store open-source em Python.",
]

def retrieve(query: str) -> list[str]:
    """Busca por keyword (em produção: embeddings + similaridade)."""
    return [d for d in KNOWLEDGE_BASE if any(w in d.lower() for w in query.lower().split())] or KNOWLEDGE_BASE[:2]

def generate(context: list[str], question: str) -> str:
    """Gera resposta usando HuggingFace com contexto injetado."""
    ctx = "\n".join(f"- {d}" for d in context)
    resp = client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct",
        messages=[
            {"role": "system", "content": f"Responda baseado APENAS neste contexto:\n{ctx}"},
            {"role": "user", "content": question},
        ],
        max_tokens=200,
    )
    return resp.choices[0].message.content

class State(TypedDict):
    messages: list[dict]
    context_docs: list[str]

def retrieve_node(state: State) -> dict:
    q = state["messages"][-1]["content"]
    docs = retrieve(q)
    print(f"🔍 Recuperados {len(docs)} docs para: {q[:40]}")
    return {"context_docs": docs}

3.9 Hands-on integrado — continuação

def agent_node(state: State) -> dict:
    resposta = generate(state["context_docs"], state["messages"][-1]["content"])
    return {"messages": [{"role": "assistant", "content": resposta}]}

# --- Grafo simples: retrieve → generate ---
def run_rag_agent(pergunta: str) -> str:
    state: State = {"messages": [{"role": "user", "content": pergunta}], "context_docs": []}
    state.update(retrieve_node(state))
    state.update(agent_node(state))
    return state["messages"][-1]["content"]

# Teste — chamadas reais ao HuggingFace!
print(run_rag_agent("O que é RAG e como funciona?"))
print(run_rag_agent("Como funciona memória persistente?"))
