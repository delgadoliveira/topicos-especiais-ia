1️⃣ Preflight & debugging

Sempre comece rodando o preflight offline. Ele isola o seu agente dos demais e diz o que está errado.

python check_agent.py agents/<seu-slug>.py
O portal também é tolerante a falhas: se seu agente quebra, ele aparece na lista de erros — mas os outros seguem funcionando.
🔍 Dica de debug: rode com MOCK_LLM=1 primeiro. Se funciona no mock e falha "de verdade", o problema é token/rede/prompt, não o seu código.

🐞 Erros comuns e como resolver

ModuleNotFoundError → dependência faltando. pip install -r requirements.txt.
HF_TOKEN não encontrado → configure o .env ou rode com MOCK_LLM=1.
slug duplicado → dois alunos usaram o mesmo. Combine e renomeie.
resposta vazia → max_tokens muito baixo ou prompt ambíguo.
timeout / 503 → modelo "acordando". O llm.chat já tenta de novo; espere e repita.
trava tudo → você fez chamada de rede no import. Mova para dentro do run().

2️⃣ Por que avaliar?

"Funcionou quando eu testei" não é medida. Um agente pode acertar hoje e regredir quando você muda o prompt amanhã.
Avaliar = ter um conjunto de casos que roda sempre e diz, objetivamente, se melhorou ou piorou.
Duas camadas: checks determinísticos (rápidos, offline) + juiz LLM (opcional, para qualidade).

2️⃣ Escreva 3 casos de teste

Crie eval/cases/<seu-slug>.yaml. Cada caso: uma entrada + o que esperar da saída.

agent: tutor-sql
cases:
  - input: "SELECT * FORM usuarios"          # erro de digitação proposital
    max_latency_s: 30
    must_contain: ["FROM"]                    # a correção precisa aparecer
    judge: "A query corrigida está sintaticamente correta?"

  - input: "SELECT nome FROM users WHERE id = "
    max_latency_s: 30
    must_not_contain: ["Traceback", "Exception"]

  - input: "obrigado!"                         # entrada fora do escopo
    max_latency_s: 30
    judge: "O agente responde educadamente sem inventar uma query?"
Inclua sempre: 1 caso feliz, 1 caso difícil/borda e 1 fora do escopo.

2️⃣ Rode o scorecard

python eval/run_eval.py tutor-sql
=== tutor-sql (3 casos) ===
✅ caso 1: juiz: SIM
✅ caso 2: ok
❌ caso 3: juiz: NÃO

📊 2/3 casos passaram.
Um ❌ não é fracasso: é informação. Ajuste o prompt, rode de novo, veja o número subir. É assim que se melhora um agente de verdade.

2️⃣ Camada 2 — o juiz LLM

Checks pegam o objetivo (contém? rápido?). Para qualidade, um modelo faz de juiz, respondendo SIM/NÃO.

# (já embutido em eval/run_eval.py — conceito)
verdict = llm.chat([
    {"role": "system",
     "content": "Você é um avaliador rigoroso. Responda APENAS 'SIM' ou 'NÃO'."},
    {"role": "user",
     "content": f"{pergunta_do_caso}\n\nResposta avaliada:\n{resposta}"},
], max_tokens=5, temperature=0.0)
passou = verdict.strip().upper().startswith("SIM")
✅ Roda só com token e sem MOCK. No mock, é pulado (não trava a aula).
⚠️ Juiz LLM não é perfeito: use perguntas objetivas e temperature=0.

3️⃣ Adicione 1 guardrail

Guardrail = uma checagem na entrada ou na saída que evita comportamento ruim. Comece com um só.

MAX_CHARS = 4000

def run(self, message, history):
    # 🛡️ guardrail de ENTRADA: tamanho e vazio
    if not message.strip():
        return AgentResult(answer="Envie um texto para eu processar.")
    if len(message) > MAX_CHARS:
        return AgentResult(answer=f"Texto muito longo (máx {MAX_CHARS} caracteres).")

    resposta = llm.chat([...], max_tokens=250)

    # 🛡️ guardrail de SAÍDA: nunca devolva vazio
    if not resposta.strip():
        return AgentResult(answer="Não consegui gerar uma resposta. Tente reformular.")
    return AgentResult(answer=resposta)

3️⃣ Menu de guardrails úteis

📏 Tamanho: rejeite entradas gigantes (custo/latência).
🚫 Fora de escopo: se não for a sua tarefa, responda educadamente e não invente.
🔒 PII: não repita CPF/e-mail/telefone na resposta (regex simples).
🔁 Anti-loop: limite de passos/chamadas se o agente iterar.
🧯 Fallback: se o modelo falhar, mensagem clara em vez de stack trace.
✅ Formato: valide que a saída tem o formato prometido (ex: JSON, lista).
O portal já te dá o fallback global (runner captura exceções). Você adiciona os específicos da sua tarefa.

4️⃣ Observabilidade — saber o que aconteceu

O portal já registra cada interação em logs/interactions.jsonl (uma linha por chamada). Segredos são redigidos automaticamente.

{"ts":"2026-10-14T20:11:03","slug":"tutor-sql","status":"ok",
 "latency_s":1.87,"input_preview":"SELECT * FORM usuarios",
 "answer_len":142,"error":null}
📊 O que medir: latência, taxa de erro, tamanho da resposta, casos sem resposta.
🔐 O que NÃO logar: tokens, dados sensíveis do usuário. Guarde só o necessário.

5️⃣ Deploy no Hugging Face Spaces (grátis)

1. huggingface.co/new-space → SDK Gradio, visibilidade pública
2. suba a pasta: app.py, requirements.txt, README.md, portal/, agents/
3. Settings → Variables and secrets → adicione o secret HF_TOKEN
4. o Space builda sozinho e publica a URL 🎉
# o topo do README.md diz ao Spaces como rodar:
---
title: Portal Multi-Agente
sdk: gradio
app_file: app.py
---
Sem Dockerfile. Sem servidor. Sem cartão de crédito. O Gradio + esse cabeçalho é tudo que o Spaces precisa.

5️⃣ Seu agente no portal comum

Duas formas de entregar. A da turma é a 2: um Pull Request com um arquivo.

Opção A — seu próprio Space. Você publica seu portal com o seu agente. Bom para portfólio.
Opção B — portal da turma. PR adicionando agents/<slug>.py + eval/cases/<slug>.yaml. Todos num só site.
git checkout -b agente-<slug>
git add agents/<slug>.py eval/cases/<slug>.yaml
git commit -m "feat: agente <slug>"
git push origin agente-<slug>      # abra o Pull Request
