Meu primeiro agente local

Um tutorial passo a passo com simulador local e uma comparação opcional com IA real.

Mapa da imersao: antes de comecar · caso resolvido · encontro 5 · encontro 6 · socorro

Antes de comecar

Produto final: um agente de tarefa unica que recebe texto, devolve uma resposta verificavel, recusa entradas inadequadas e registra o que aconteceu.

Regra principal: tudo deve funcionar com MOCK_LLM=1. Nesse modo, nenhum modelo de IA e executado. A API real e apenas uma comparacao controlada no final.

0. Entenda de onde vem cada resposta

Modo padrão — simulador local

entrada → agente → função Python → resposta [MOCK]

  • Modelo de IA: nenhum.
  • API, token ou internet: não precisa.
  • O que faz: repete parte da entrada de forma previsível.
  • O que comprova: código, fluxo, formato, guardrails e testes.

Modo opcional — IA real

entrada → agente → API Hugging Face → Qwen → resposta

  • Modelo: Qwen/Qwen2.5-7B-Instruct.
  • Onde roda: infraestrutura do Hugging Face.
  • O que precisa: internet e HF_TOKEN.
  • Limite da aula: até três chamadas planejadas.
Importante:

O mock não “pensa”, não interpreta o prompt e não mede a qualidade da IA. Ele é um simulador para aprender a construir e testar o sistema. A qualidade generativa só pode ser comparada no modo de API real.

Caso pedagógico resolvido — Organizador de Estudos

Antes de criar seu próprio agente, acompanhe uma solução completa para o problema de Ana. O objetivo não é copiar o tema: é enxergar como uma ideia vira contrato, código, teste, melhoria e evidência.

1 · Situação

Ana tem prova, várias matérias e pouco tempo. Ela não precisa de “uma IA que sabe tudo”; precisa decidir por onde começar.

2 · Promessa

Receber matérias, prazo e tempo disponível. Devolver um plano curto com prioridades e próximo passo.

3 · Primeira versão

Definir identidade, validar a entrada, escrever a instrução e chamar o simulador local.

4 · Evidência

Rodar um caso normal, um difícil e um vazio. Cada teste traduz uma parte da promessa.

5 · Melhoria

Adicionar limites para entrada vazia e texto muito longo; depois executar os mesmos testes novamente.

6 · Reflexão

O mock prova fluxo e formato, mas não prova a qualidade semântica de uma API real. Essa limitação deve ser explicada.

A implementação completa

O exemplo executável está em agents/organizador-estudos-referencia.py. Leia de cima para baixo e localize identidade, guardrails, instrução, chamada ao modelo e resposta.

from portal import llm
from portal.base import AgentResult


class OrganizadorEstudosReferencia:
    slug = "organizador-estudos-referencia"
    name = "Organizador de Estudos (referência)"
    emoji = "📚"
    description = "Exemplo resolvido: transforma anotações em um plano curto."

    def run(self, message, history):
        text = message.strip()
        if not text:
            return AgentResult(
                answer="Envie matérias, prazo e tempo disponível para eu organizar.",
                steps=["Entrada vazia recusada"],
            )
        if len(text) > 4000:
            return AgentResult(
                answer="O texto é muito longo. Envie até 4.000 caracteres.",
                steps=["Limite de tamanho aplicado"],
            )

        steps = ["Validei a entrada", "Pedi três prioridades ao modelo"]
        resposta = llm.chat(
            [
                {
                    "role": "system",
                    "content": (
                        "Você é um organizador de estudos acolhedor. "
                        "Transforme as informações em exatamente três prioridades. "
                        "Para cada uma, informe assunto, motivo e uma ação de até "
                        "20 minutos. Não invente dados ausentes."
                    ),
                },
                {
                    "role": "user",
                    "content": f"Crie um plano para estas informações:\n{text}",
                },
            ],
            max_tokens=250,
        )
        steps.append("Organizei a resposta no formato combinado")

        return AgentResult(
            answer=(
                "Plano de estudo\n\n"
                f"{resposta}\n\n"
                "Próximo passo: escolha a primeira prioridade e comece agora."
            ),
            steps=steps,
        )


AGENT = OrganizadorEstudosReferencia()

Execute o caso antes de modificá-lo

python check_agent.py agents/organizador-estudos-referencia.py
python eval/run_eval.py organizador-estudos-referencia
Resultado esperado

8. Adicione um guardrail simples

No metodo run(), antes de chamar llm.chat(...), trate entrada vazia e muito longa:

text = message.strip()
if not text:
    return AgentResult(
        answer="Envie algum texto para eu organizar.",
        steps=["entrada vazia recusada"],
    )
if len(text) > 4000:
    return AgentResult(
        answer="O texto e muito longo. Envie ate 4.000 caracteres.",

Rode novamente o preflight e a avaliacao.

9. Observe antes de corrigir

python app.py

No portal, confira os passos e a latencia. No terminal, observe o log JSON: agente, modo, duracao e resultado. O rodape informa simulador local · nenhum modelo de IA ou identifica o modelo real e o numero de chamadas.

10. Compare com a API real — opcional e coletiva

Orcamento: no maximo tres chamadas por grupo. O professor libera este passo. Se houver erro 429, 503, token ausente ou rede instavel, volte ao simulador local; a atividade continua valida.

A API OpenAI-compatible descreve o formato técnico da chamada; isso não significa usar um modelo da OpenAI. O modelo configurado e o Qwen/Qwen2.5-7B-Instruct, servido pelo Hugging Face.

Crie um arquivo .env baseado em .env.example e altere:

HF_TOKEN=seu_token
MOCK_LLM=0
MAX_REAL_CALLS=3
LLM_CACHE=1

Reinicie o portal. Use exatamente uma entrada dos seus testes, repita a mesma entrada para observar o cache e use uma terceira entrada somente se precisar comparar.

Nunca: cole o token no arquivo do agente, em prints, screenshots, commits ou mensagens. O arquivo .env e local.

12. Prepare a demo de dois minutos

  1. 20s: quem voce ajuda e qual tarefa resolve.
  2. 40s: uma entrada e a resposta.
  3. 30s: um teste que falhou e a melhoria feita.
  4. 20s: guardrail e log.
  5. 10s: uma limitacao conhecida.
Definition of Done
  • Preflight passa offline.
  • Tres casos de teste foram executados.
  • Ha pelo menos um guardrail.
  • A demo funciona mesmo sem rede.
  • O ZIP foi criado e avaliado.
  • O aluno consegue explicar uma limitacao.
